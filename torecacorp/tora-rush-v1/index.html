止める位置（この映像の場合）

ゲーム映像の切れ目リールを静止画で覆う文字が出きって止めるタップ後の再開
  • 順番：キャラ → 「7を揃えてコンボを決めろ！」が出る → タップ待ち → タップでリールが回る
  • 映像では文字が出るのとリールが回りだすのがほぼ同時（頭から約0.43秒でリールが回りだし、文字が出きるのは約1.0秒）。そこで、頭から0.3秒の時点でリール部分を「止まったリールの静止画」で覆い、文字が出きる1.0秒で映像を止めてTAPを出す
  • タップすると、リール部分に光のフラッシュを出して静止画を外し、1.0秒の位置から再生（リールは回っている状態から続く）
  • 2ゲーム目はハズレ→復活の流れ。復活は映像の中で起きるので、途中でタップは要らない
  • 覆う静止画は、各ゲームの頭から0.3秒のコマのリール部分（画面の下37.5%、上端はスロット台の枠）を切り出したもの。境目が台の枠なので、つなぎ目は目立たない
  • いちばん自然なのは、映像側で「文字が出きってからリールが回りだす」ように直してもらうこと。その場合は静止画で覆う処理が要らない
ひと言でいうと：ガチャで当たった景品の相当額を、先にサーバーで「7揃いの組み合わせ」に分けておき、ユーザーのタップごとにリール映像（MP4）を1本ずつ再生していく演出です。最後に、揃った7の種類と数をリザルトに並べて終わります。
当たる景品はガチャの抽選で先に決まっていて、演出は結果を見せる方法にすぎません。演出で確率や還元率は変わりません。

4. 演出の組み立てロジック（サーバー）

4-1. 入力と出力

入力当たった景品の相当額 A（景品に登録済みのコイン還元額を使う 提案）、7の種類マスタ、映像クリップマスタ
出力再生リスト（クリップIDの並び）、リザルト（7の種類ごとの個数、合計獲得数、合計相当額）。抽選結果と一緒にDBに保存する

4-2. 組み合わせの作り方 提案

  1. 残り R = A とする
  2. R 以下の額になる「7の種類 × ライン数（1ライン／ダブルライン）」の候補から、出やすさの重みで1つ選ぶ
  3. 選んだ額を R から引き、ゲームを1つ追加する。R が一番小さい7の額を下回るまで繰り返す
  4. ゲーム数が上限（例：10ゲーム）を超えそうなら、大きい額の候補を優先して本数を抑える v0.2 1ゲーム約11秒のため、10ゲームで約2分。30ゲームだと5分を超える
  5. 最後に残った R（最小の7に満たない端数）の扱いは 未決事項 の Q3
  6. 並び順をシャッフルする。そのうえで次のルールを当てる
    • 最後のゲームは、そのラッシュで一番大きい7にする（盛り上がりで終わる）
    • 復活演出は、1ゲーム目以外にランダムで入れる（出す割合は管理画面で設定）
  7. 各ゲームについて、同じ7・同じライン数のクリップが複数あればランダムに1本選ぶ（停止順・リーチ目の違いで見た目を変える）

例：A＝55万相当 → 赤7（10万）×3、緑7（5万）×1、金7（20万）×1 … のように毎回違う組み合わせになる（色と額は仮。Q1）。合計は必ず A（端数を除く）と一致させる。

4-3. 守ること

  • 演出の合計は、付与した景品の相当額と必ず一致させる（演出と実際の景品がずれると誤認の原因になる）
  • 再生リストはサーバーで作って保存し、画面側では作らない。リロードや履歴から開いても同じ演出になる
  • 演出の途中で景品やptを付与しない。付与はガチャ確定時に一度だけ行う（既存のガチャと同じ）

9. 動作環境と懸念点

懸念対応
iPhoneで音つき動画が自動再生されない毎ゲームをタップで再生する作りなので、タップの処理の中で play() を呼べば音つきで再生できる。playsinline を必ず付ける
BGMと動画の音が重なる・止まるBGMも最初のタップで再生を始める。端末によってはBGMが止まるので、止まったら次のタップで再開する

12-1. レートは設定できるか

12-3. 映像の設定方法

  1. クリップを登録する（管理画面「RUSH映像」）：MP4をアップロードし、区分（OP／通常ゲーム／復活ゲーム／TOTAL／ハズレ目）、色（緑・赤・金・虹）、ライン数を選ぶ
  2. 止める位置を決める：プレビューを見ながら「リールを覆い始める位置」と「タップ待ちで止める位置」をボタンで指定する（初期値は0.3秒と1.0秒）。止まったリールの静止画は、指定した位置のコマからサーバーで自動で切り出す
  3. 演出セットにまとめる：OP・各色の通常／復活・TOTAL・BGM・タップ表示の文言を1つのセットにする（例：「虎巻ATTACK 通常」「虎巻ATTACK 極」）。足りないクリップがあるとセットを有効にできない
  4. BOXでセットを選ぶ：BOX編集で演出タイプ「虎巻ATTACK」と演出セット、RUSHレートを選ぶ

同じ色のクリップを複数登録すると、ゲームごとにランダムで選ばれる（見た目のバリエーション）。後からクリップを足しても、BOXの設定は変えなくてよい。

12-4. ガチャ作成画面（BOX編集）

景品の登録は今までどおり（カード・状態・口数・コイン還元額）。そこに「この景品が当たったら、7がどう揃うか」を自動で計算して横に出します。7の組み合わせは手で組むのではなく、景品の相当額から毎回自動で作るので、景品を登録すれば演出も決まります。管理者は内訳の例を見て、意図どおりか確認するだけです。

BOX編集 ＞ 演出設定 （モック）
景品口数相当額7の内訳（例・毎回変わる）ゲーム数確認
「試し再生」で、その景品が当たったときの流れをモック（3章）で再生します。警告：7が揃わない景品・端数が出る景品・ゲーム数が上限に近い景品

12-5. サーバー負荷

どこ負荷対策
抽選（DB・API）ほぼ増えない。7の組み合わせを作る計算は1回あたり1ミリ秒未満で、抽選と同じ処理の中で行う。保存するのは1回あたり1KB前後のJSON特になし。10連・100連でも件数分の計算で済む
映像の配信一番大きい。1回のプレイで OP約2MB＋1ゲーム約2MB×ゲーム数＋TOTAL約1MB。例：6ゲームで約15MB。ただし同じクリップを使い回すので、2回目以降は端末に残ったものを使い、ほとんどダウンロードしない（初弾17本で約35MB）アプリのサーバーやDBからは配らず、CDNから配る。ファイル名に版を入れて長くキャッシュさせる。転送量で費用が決まるので、転送料のかからないストレージ（例：Cloudflare R2）も候補
同時アクセス（公開直後・イベント）映像はCDNが受けるので、アプリ側は通常のガチャと同じ公開前にクリップを一度CDNに読み込ませておく

目安：1日5,000回プレイ・キャッシュに当たる割合50%なら、配信は1日約40GB（月1.2TB程度）。実際の費用は配信先の料金で変わる。

12-6. タップでリールを回す動きは、端末やブラウザが違っても安定するか

次の作り方なら、主要な端末（iPhoneのSafari・Chrome、AndroidのChrome、LINE・Xのアプリ内ブラウザ）で同じように動かせます。9割カバーの目標には届く見込みです。

心配作り方
音つきで再生できない（iPhone）再生は必ずタップの処理の中で始める。毎ゲームをタップで再開する作りなので、ここは有利。playsinline を付けて全画面にならないようにする
止める位置がずれる映像のコマ単位で通知を受けられる requestVideoFrameCallback で止める（iOS 15.4以降・Chrome・Edgeが対応）。対応していないブラウザは画面の書き換えごとに位置を見て止め、1コマ（約0.03秒）以内のずれに収める。ずれてもリール部分は静止画で覆っているので見た目に出にくい
静止画と映像の位置がずれる映像と静止画を同じ9:16の枠に入れ、枠の比率を固定する。画面サイズが違っても同じ割合（下37.5%）で重なる
連打・二重タップタップ待ちのときだけ受け付け、受け付けたら次の停止まで無視する
読み込みが遅い・回線が弱い前のゲームを見ている間（約11秒）に次のクリップを読み込む。間に合わなければタップ表示の代わりに「読み込み中」を出す。5秒たっても再生できなければ、そのゲームを飛ばす（景品は付与済み）
省電力モード（iPhone）自動再生は止められるが、タップで再生するので影響しない。先読みが効かない場合があるので、上の「読み込み中」で対応
BGMだけ鳴らないiPhoneはマナーモードで鳴り方が変わる場合がある。BGMは <audio> で鳴らし、最初のタップで再生を始める
アプリを切り替えた・画面を離れた映像とBGMを止め、戻ったらタップ待ちから再開する

開発の最後に実機で確認する（iPhone 2〜3機種・Android 3機種程度、LINE・Xのアプリ内ブラウザ）。試作は同じ止め方で作ってあるので、手元のスマホで開くと今の時点の動きを確認できる。
